2 · Architecture & Application Flow

Uzhavan Direct is a single‑page application with imperative rendering. There is no virtual DOM: each view is a function that receives the #viewRoot element, clears it, and builds DOM nodes (mostly via innerHTML templates plus document.createElement for interactive parts).

Boot sequence

  1. Seed — seed() populates demo users, produce, orders, auctions and demand (guarded once by ud_seeded_v2).
  2. Migrations — ensureConsumerProfileFields(), ensureDemoCredentials() (ud_demo_credentials_v2), and ensureFpoPortalData() (ud_fpo_v1) are non‑destructive and each run only once.
  3. Auth gate — ud_currentUser is deleted on load and currentUser = null, so a fresh login is required on every page visit.
  4. Theme & language — saved ud_theme, ud_color_mode and ud_lang are re‑applied before first paint.
  5. Shell render — boot() unhides #appShell, resolves the role from the user record, builds the role‑specific sidebar via renderNav(), and draws the dashboard via renderView('dashboard').

Routing model

Routing is a two‑level dispatch: renderNav() picks the sidebar array for the current role, and renderView(viewId) picks the matching render function from a per‑role map. Views that are not in the sidebar (profile, settings, sub‑lists) still resolve through EXTRA_VIEW_TITLES so the topbar title is never a raw id.

goTo(viewId) → renderNav() + renderView(viewId) → render<Role><View>(root)

3 · Roles & Authentication

Three roles share one auth screen. A segmented role switch selects the intended account type, and the login form validates that the entered credentials actually match that role.

RoleDemo accountPasswordPurpose in the system
farmerkarthik_farms / meena_agro123 / pass123Lists produce, runs auctions, sees market demand, uses the AI advisor, manages sales.
consumerdivya_buys123Shops, bids, tracks deliveries on the map, follows and rates farmers, donates.
fpothanjai_fpo123Runs first‑mile aggregation, corridor batching and destination‑hub dispatch.

A single universal demo shortcut exists: entering john / 123 logs in as whichever role is currently selected — the app maps the shorthand through DEMO_LOGIN_USERS to the correct role account.

Authentication features

  • Role‑aware login — credentials are matched, then the record's type must equal the selected role.
  • Username or phone login — the identifier field accepts either.
  • Sign‑up with demo OTP — name, username, 10‑digit phone and password; an on‑screen demo OTP must be verified before the account is created.
  • Role‑specific profile fields — farmers get village/bio; consumers get city/address; FPOs get source cluster and destination hub.
  • Session feedback — a user chip shows the display name; a logout button returns to the auth screen.
  • Password migration — ensureDemoCredentials() normalises the older meena_agro password so all demo logins behave predictably.

4 · Complete Feature Catalogue

4.1 · Farmer module

Dashboard

  • Stat strip — Pending Sales, Completed Sales, Total Income (completed order value plus donations received). Each tile is click‑through to its detail view.
  • “Your produce listings” — grid of the farmer's own listings with photo, category, stock, per‑unit price and a freshness badge (“Keeps …”), or a friendly empty state.

Sell Produce

  • Create a listing with name, category (grains/cereals/pulses, vegetable, fruit, dairy), quantity, unit and price.
  • Automatic enrichment — iconFor() assigns an emoji, guessPerishability() computes a shelf‑life label, and productImageUrl() resolves a bundled photo for 15 known products.
  • Photo upload with client‑side compression — compressProductImage() downscales an uploaded image before it is stored as a data URL.

Auctions & bidding

  • Farmer‑created auctions carry a base rate, quantity, unit and an automatic end time.
  • Live count‑down timers via tickTimers(); closeAuctionIfNeeded() closes an auction when it expires.
  • Highest‑bid tracking — shows the current highest bid and bidder; placeBid() validates that a new bid beats the standing one.

Market Demand

  • Bar‑style visualisation of historical demand across ~10 commodities (rice, tomato, onion, milk, mango, carrot, toor dal, banana, potato, eggs).

Farm Advisor (AI chat)

  • Conversational assistant with suggested prompts (“Today's market rate for tomato”, “What crop should I grow?”, “How do I list a new produce?”, “Help”).
  • Rule‑based reply engine — craftChatReply() handles greetings, keyword‑matched market rates from MOCK_RATES, crop guidance and listing help; unknown input falls back gracefully.

Sales management

  • Pending Sales — per‑order rows with a status control and an “Advance tracking” button that moves the order one step along the delivery pipeline.
  • Completed Sales — delivered/closed orders.
  • Money Details — a ledger view of income, including donations received.

Farmer profile & settings

  • Profile card (name, village, bio, rating average) plus follower count.
  • Settings: appearance (bright/dark), colour theme picker and language switch — shared with all other roles.

4.2 · Consumer module

Dashboard

  • Stat strip — Purchased Items (active, non‑refunded, undelivered orders) and Total Spent (purchases plus donations made).
  • “Fresh from nearby farmers” — the first four available listings, each with an Add to cart button.

Nearby Produce & Search

  • Nearby Produce — full masonry‑style grid of all unsold listings; clicking an item opens the quantity picker.
  • Farmer browse — per‑farmer produce views (showFarmerProduce).
  • Search Produce — searches across produce and farmers; results split into a produce list and a farmer result‑card list with an explicit empty state.

Basket, quantity picker and checkout

  • Quantity picker modal — ± stepper, live unit label and a running total (Add to cart · ₹…) before anything is added.
  • Cart drawer — slide‑in panel with line items, per‑line quantity changes, remove buttons, a live subtotal, and a delivery hint (“Direct from local farmers · No middlemen commission”).
  • Cart badge in the topbar keeps the item count visible at all times.
  • Animations & sound — animateAddToCart() flies the product image toward the cart; playCartPopSound() and playCheckoutChime() provide Web Audio feedback (generated, no audio files).
  • Address gate — checkout is blocked until the consumer's city/address is complete, with a redirect into profile settings to fix it, and the cart is resumed afterwards.

Payment modal (demo)

  • Four methods: Google Pay, Credit/Debit card, UPI, Cash on Delivery.
  • A demo OTP is generated per modal open and displayed on screen; “Verify & Pay” checks the entered code, then completeCheckout() converts each cart line into a real order and reduces listing stock.

Order tracking & history

  • Purchased Items — active orders grouped by farmer/product with live stage badges.
  • Purchase History — past orders, with a rate‑and‑review entry point.
  • Track Delivery modal — see §5.
  • Money Details — spend ledger including donations.

Social, ratings & donations

  • Follow / unfollow farmers — a “Farmers You Follow” view mirrors followers[] on the farmer record.
  • Farmer public profile — bio, village, produce and aggregate star rating.
  • Rating modal — 1–5 stars plus an optional comment; re‑rating a farmer updates the existing entry rather than duplicating it (recordRating).
  • Donation modal — a consumer can donate to a farmer; donations are written to a shared ledger (ud_donations) and appear in both the donor's “Total Spent” and the recipient's “Total Income”.
  • Notification bell — unread badge plus a dropdown; used for donation alerts and FPO logistics alerts.

5 · Order Tracking Pipeline

Every order carries a single deliveryStage. That one field drives three surfaces at once — the farmer's order‑management view, the consumer's purchased‑items list, and the consumer's tracking timeline — so the three can never disagree.

#StageMeaning
1placedOrder placed by the consumer; awaiting farmer confirmation.
2confirmedFarmer has confirmed the sale.
3packedProduce harvested/packed and ready to leave the farm.
4atFarmerCityOrder has reached the farm‑side city / collection point — the entry point for FPO aggregation.
5atCustomerCityLong‑haul leg complete; order is in the customer's city.
6atFpoOrder has arrived at the FPO destination hub.
7outForDeliveryHanded to a last‑mile (EV) delivery agent.
8deliveredDelivered — order status is simultaneously set to completed.

The tracking modal

  • Vertical timeline — Amazon‑style progression with done / current / upcoming states and per‑stage descriptions.
  • Leaflet live map — markers for the farm, intermediate cities and the destination hub, with the route drawn between them.
  • Route HUD — road distance (km), estimated travel time, and the city route (e.g. Salem → Chennai), computed haversine‑style from CITY_COORDINATES.
  • Delivery‑schedule form — once an order reaches the hub, the consumer picks a time slot (Morning / Afternoon / Evening / Custom date+time) which is persisted as fpoDeliveryTiming.
  • Advance Tracking — steps the order one stage forward with a toast confirmation.
  • Live subscription — the modal registers a ud-stage-changed listener, so if an FPO (or farmer) advances the order while the modal is open, the timeline re‑renders and the map re‑pans without a reload. The listener is detached on close to avoid leaks.

The single writer

setOrderStage(orderId, stage, extraFields) is the one function that mutates a delivery stage. It:

  1. persists the new deliveryStage;
  2. sets status = 'completed' when the stage is delivered;
  3. optionally co‑writes extra fields (e.g. fpoDispatchedAt); and
  4. dispatches a ud-stage-changed custom event on window.

Both the farmer's advanceOrderStage() and the legacy updateOrderStatus() now delegate to it, which is what makes cross‑role live updates possible.

Legacy‑data migration

Older orders have no deliveryStage. getOrderStage() derives one from status and rewrites two historic names — atFarmerFpo → atFarmerCity and atCity → atCustomerCity — so seeded data keeps working.

6 · FPO Manager Portal — Three Logistics Tiers

The FPO portal layers a producer‑organisation logistics network on top of the shared order model. It is available to the fpo role and is organised as three sequential tiers, each mapped 1:1 to a sidebar entry.

6.1 · Logistics dashboard

  • Stat strip — Pending Tier‑1 aggregations (lots awaiting grading), Total batch weight in Tonnes, Active transit corridors, and Hub delivery queues.
  • Three tier cards — a visual pipeline (Tier‑1 → Tier‑2 → Tier‑3) with live throughput counts, each clickable straight into its tier.
  • Batch activity list — recent corridor shipments with corridor name, status chip (Assembling / In transit / Received at hub), vehicle type, weight and order count.

6.2 · Tier‑1 — First‑Mile Aggregation & AGMARK Grading

Handles produce arriving at village farm‑gate collection points.

ElementBehaviour
Awaiting‑grading tableEvery order at atFarmerCity with no grade yet: order id, source farmer & village, produce, and the ordered quantity.
Digital weighment loggerA numeric input per row (.fpo-weigh-input) captures the actual weighed quantity, independent of the ordered quantity.
AGMARK quality pickerThree grades — A · Premium, B · Standard, C · Processing — selected per row.
Confirm gradingconfirmFpoGrade() validates that both a weight and a grade are set, then stamps fpo, fpoGrade, fpoWeighKg and fpoGradedAt and moves the order into the batching queue.
En‑route rowsOrders still in packed are listed separately so the manager can see inbound volume.
Graded & queued tableGraded lots with a colour‑coded grade badge, weight, and either “Awaiting corridor batch” or the batch id they joined.

6.3 · Tier‑2 — Consolidated Freight Corridor Batching (LTL)

Consolidates many small lots into one shipment — Less‑Than‑Truckload aggregation.

  • Corridor selector — preset Tamil Nadu freight routes: Nilgiris → Thanjavur, Salem → Chennai, Erode → Coimbatore, Trichy → Madurai.
  • Vehicle selector — 3‑Tonne shared truck (3,000 kg) or Kisan Rail parcel van (5,000 kg).
  • Live capacity meter — as lots are ticked, a progress track and label show loaded weight against vehicle capacity, and turns to an over‑capacity warning state.
  • Queue list — every graded‑but‑unbatched lot with a checkbox, id, item and weighment.
  • Create batch — createFpoBatch() requires a selection, rejects loads exceeding vehicle capacity, then writes a shipment record (status: assembling) and stamps each order with fpoBatchId, fpoCorridor and fpoVehicle.
  • Dispatch — dispatchFpoBatch() flips the batch to dispatched and advances every batched order to the atFpo stage in one action, recording fpoDispatchedAt.
  • Batch cards — each shipment shows corridor, vehicle, weight, order count, status chip and its dispatch control.

6.4 · Tier‑3 — Destination Hub De‑batching & Last‑Mile Dispatch

  • Incoming shipments — every dispatched corridor shipment with a Receive button; receiving (receiveFpoBatch()) sets the batch to received and stamps receivedAt.
  • Hub delivery queue — orders at atFpo awaiting doorstep delivery.
  • Consumer delivery slots — each row shows the slot the consumer chose in the tracking modal (e.g. “Morning (8:00 AM–11:00 AM)”, or an explicit “Awaiting consumer slot” chip).
  • EV agent assignment — a dropdown of EV doorstep agents (Kumar · EV‑01, Anitha · EV‑02, Selvam · EV‑03).
  • Guard rail — assigning an agent is blocked until that order's corridor shipment has been received, with the toast “Receive the corridor shipment first”.
  • Assign & dispatch — assignFpoEvAgent() stamps fpoEvAgent / fpoEvAssignedAt and advances the order to outForDelivery.
  • Last‑mile list — orders already out with an EV agent, so the hub can see its live doorstep workload.

6.5 · Consumer notification on every FPO action

Each FPO transition calls notifyOrderConsumer(), which appends a message to the consumer's notifications[] array and refreshes the notification‑bell badge — so grading, dispatch and EV assignment all surface as alerts on the consumer's side.

End‑to‑end FPO flow

atFarmerCity · ungraded → weigh + AGMARK grade → batch queue → tick lots → create batch → assembling → dispatch → atFpo → receive → received → assign EV agent → outForDelivery → delivered

Every arrow above is a setOrderStage() call, so the consumer's open tracking modal updates live at each step.

6.6 · FPO profile & settings

  • Profile — organisation card plus an operations snapshot (lots handled, batches created, total tonnage).
  • Settings — the shared appearance/theme/language panel plus cluster and hub profile fields.

8 · UI / UX Systems

Design tokens

CSS custom properties drive colour, radius and shadow throughout: --forest, --forest-dark, --turmeric-dark, --paper, --card, --line, --ink-soft, --danger, --success, --radius-sm/md, --shadow.

Theming

  • Three palettes — Harvest (default), Emerald and Teal — applied via a data-theme attribute on <html>.
  • Light & dark mode — a separate data-color-mode-style switch covering every component (FPO surfaces included).
  • Theme‑aware browser chrome — the <meta name="theme-color"> tag is updated whenever the palette changes, so mobile browser UI matches.
  • Theme picker — swatch menu with the palette name and a preview of its four colours.

Localisation

Full three‑language UI dictionary (English, Tamil, Hindi) covering navigation, dashboard labels, orders, money, appearance and all FPO tier names. t(key) resolves the active language with an English fallback, and the brand name and tagline are localised too (e.g. உழவர் சந்தை / किसान मंडी).

Interaction & feedback

  • Toasts — a single reusable toast() surface used for successes, guards and errors.
  • Modals — quantity picker, payment, tracking, rating and donation overlays, all built on a shared .modal-overlay pattern with ARIA roles and labelled close buttons.
  • Web Audio feedback — synthesised cart‑pop and checkout‑chime sounds; no audio assets required.
  • Fly‑to‑cart animation — the product image animates into the cart button on add.
  • Status & grade badges — colour‑coded chips for delivery stages and AGMARK grades.
  • Capacity meter — a live fill track that warns when a batch exceeds vehicle capacity.

Layout & responsiveness

  • Fixed sidebar + scrolling main area with a collapsible mobile drawer (menuToggle).
  • Responsive produce grid, stat strip that wraps to two columns under 900 px, and full‑width form controls on small screens.
  • Card‑based composition throughout: .card, .section-head, .order-row, .empty-state.
  • Motion is honoured: a prefers-reduced-motion block disables transitions for users who ask for it.

Empty states

Every list view ships a friendly empty state with a glyph and a call to action (no listings, no orders, no search results, no batches), so no screen is ever blank.

9 · Backend API (server/)

A complete Express + PostgreSQL service sits alongside the SPA. It is not yet connected to the frontend — it runs standalone with its own integration suite — and it mirrors the same order pipeline and FPO concepts as the client.

EndpointMethodPurpose
/api/auth/registerPOSTCreate a farmer, consumer or FPO account.
/api/auth/loginPOSTCredential login returning a JWT.
/api/auth/meGETCurrent authenticated user profile.
/api/auth/request-otpPOSTIssue a phone OTP (stored in otp_codes).
/api/auth/verify-otpPOSTVerify an OTP and complete registration.
/api/produce · /api/produce/:idGET / POST / PUTBrowse, create and update produce listings.
/api/auctions · /api/auctions/:idGET / POSTList auctions and create new lots.
/api/auctions/:id/bidPOSTPlace a bid with validation against the standing highest bid.
/api/orders · /api/orders/:idGET / POST / PATCHCreate and read orders; patch order fields.
/api/orders/:id/stagePATCHServer‑side equivalent of the client's setOrderStage() — advances an order along the pipeline with FPO stage‑band rules.
/api/fpo/batchesGET / POSTList this FPO's shipments; create one — attaching orders assigns them to the FPO.
/api/fpo/batches/:idGET / PATCHRead or update a batch's status, details and attached orders.

Database schema

Six tables: users, otp_codes, produce, auctions, orders and fpo_batches.

Server‑side safeguards worth noting

  • JWT authentication with role‑based route guards (requireRole('farmer' | 'fpo' …)).
  • bcrypt password hashing (contrast with the frontend demo, which stores plaintext).
  • Ownership checks before writes — e.g. assertAttachable() rejects orders that belong to another FPO with a 409 ORDERS_NOT_ATTACHABLE error listing the offending ids.
  • Transactional batch attachment — withTransaction() keeps multi‑order updates atomic.
  • Typed error responses through a shared HttpError + asyncHandler pattern.
  • 25/25 integration tests running against an in‑memory Postgres (pg‑mem), so no database is required to verify the API.

Known interface difference to reconcile

The frontend's stage list contains eight stages including atCustomerCity, while the server's DELIVERY_STAGES models a seven‑stage band. Any wiring work must map the client's extra stage onto the server model — the server README already records this discrepancy.

10 · Current Limitations

An honest list of what is not yet in place, so the demo is not over‑sold.

AreaStatus
Frontend ↔ backend wiringThe SPA has no API client. All reads/writes are localStorage; the Express service is not called by the UI.
Authentication strengthDemo‑grade: passwords are stored in plaintext in localStorage, and OTPs are displayed on screen rather than sent by SMS.
Real paymentsSimulated. The payment modal verifies a generated demo OTP; no gateway is integrated.
User‑generated content safetySeveral views interpolate user input straight into innerHTML (search results in particular), which is a DOM‑XSS exposure.
Robustness edgesrenderDemand() assumes a non‑empty demand object; getUser() re‑parses localStorage on every call; the auction tickTimers() interval is never cleared.
Money reporting“Total Spent” currently includes refunded orders.
AccessibilityModals lack Escape‑to‑close and a focus trap; most overlays do not restore focus on close.
Third‑party weightLeaflet, Google Fonts and map tile/geocoding services are loaded from the network, so the app needs connectivity for the map view.
Build toolingNo package manifest, bundler, linter or frontend test suite at the repository root.
